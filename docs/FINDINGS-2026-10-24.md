## 已确认缺陷（本轮修复）

### D1 (P1)：client fetchState 错误分支 ReferenceError —— 错误横幅死代码

- 位置：`plugin/lib/client.mjs`（及构建产物 `client.js`）
- 根因：2026-10-23 把轮询从"序号"重构为"代际"时，`catch` 分支遗留未定义的
  `mySeq` 引用（`if (mySeq >= pollState.appliedSeq) setError(...)`）。
  任何 `/heartbeat/api/state` 获取失败（sidecar 挂 / 网络断 / 非 200）都会在该分支
  抛 `ReferenceError` → `setError` 永不执行 → **错误横幅永远不显示，面板静默
  展示过期数据**。这正是本项目审计史反复消灭的"静默失败/假健康"类别，而且恰好
  发生在为它建的可观测性防线本身。
- 复现：`verify-client-repro.mjs`（静态：mySeq 出现 1 次 0 声明；运行时：桩 fetch
  失败 → ReferenceError，error 状态盒恒为 null）。
- 修复：改为与成功路径一致的代际判断 `if (myToken === pollState.activeToken)`；
  清理死字段 `seq/appliedSeq`；重建 `client.js`。
- 回归：`plugin/test/client-error-path.test.mjs`（失败路径生效 / 成功路径无扰 /
  旧代迟到失败不覆盖新代状态）。

### D2 (P2)：熔断（auto-off）状态不持久化 —— 重启后被 ensure 绕过

- 位置：`sidecar/sidecar.js` `persistPings()` / `loadPersistedPings()`
- 根因：`runPing` 的 auto-off 分支注释声称"熔断标记（2026-10-23）：必须可持久，
  供 ensure 识别"，但 `persistPings` 对 `!p.on` 的条目一律跳过（用户显式 OFF 与
  熔断不区分），`loadPersistedPings` 亦然。于是：熔断 → sidecar 重启 → pings map
  无该条目 → ensure 的 `breakerOpen` 判空 → full-reset **重新开 ping**。2026-10-23
  审计第一批修的"熔断被对账绕过"在重启场景下名存实亡（插件侧 blockedReason 能兜
  住一半场景，但 sidecar 单独重启/崩溃后，下一轮对账即重新 ensure）。
- 复现（黑盒、全隔离场景）：熔断 → `pings.json` 中该 key 条目被删除 → 新实例加载
  同一 persist 目录 → `POST /control/on {action:'ensure'}` 返回 **200 +
  immediatePing:true 并真的向上游补发 ping**（应答 409 breaker-open）。
- 修复：
  - `persistPings`：`on=false` 且带 `autoOffedAt` 的条目作为"熔断记录"持久化
    （用户显式 OFF 仍不落盘）；磁盘旧条目的保留条件同步扩展。
  - `loadPersistedPings`：恢复熔断记录为 `on:false + stale:true + autoOffedAt/
    blockedReason`，**不**启动定时器；返回值新增 `breakers` 计数。
  - `/control/off`：显式关闭同时清 `autoOffedAt/blockedReason`（用户意图优先于
    熔断记忆，且防止已删条目被 persistPings 复活）。
  - TTL 沿用 `MAX_PERSIST_AGE_MS`（12h）兜底。
- 回归：`sidecar/test/sidecar.test.mjs` 新增 2 项（熔断跨重启持久化/恢复不建
  定时器；显式 OFF 清标记后不得复活）。

- 2026-10-22 审计 §6-d 修了 `package.json`（0.2.0）却漏了 `dsh.plugin.json`。
