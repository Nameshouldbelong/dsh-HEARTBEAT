## 事故回顾：为什么必须做 v2

2026-10-21 17:42，LSD1 会话（`session-9b9b963c…`）空窗 6h16m 后首次对话，
一次冷读 **464,378 token**，占 5h 滚动窗口约 15%。

根因不是「cache 没保住」这么简单，而是**保温打在了错误的 key 上**：

- `state.json` 里该会话的 key 是 `dshsc-ea64f39ed24bda17` —— 这是 10-20 做 E2E 验证时
  留下的 **90 token 假前缀测试 key**；
- sidecar 从 00:22 到 09:54 共 ping **34 次，每次 prompt=90 / cache_read=90**，全部报 `hit`；
- UI 一直显示健康，但**真实会话（真实前缀 464k–531k）从未被保温**；
- 真实流量的 key 是 `dshsc-19c9a0768c0a9503`，与会话日志 turn15 step1 的
  `inputTokens: 464378` 逐字节对得上。

暴露的两个机制缺陷（本次全部堵掉）：

1. **KI-1 亲和键碰撞**：旧 key = `sha256(system[:8000])`，同 preset 的多个会话共用同一 key，
   `recordedRequests` 互相覆盖；
2. **KI-3 key 轮换的副作用**：`rotateStaleKey` 用「10min 内最新活跃 key」猜当前会话，
   多会话并发时必然张冠李戴，把 E2E 测试 key 认成了 LSD1 的 key。

## 用户裁定 5 条与实现

### 1）关闭 caching 总额上限（✅ 已实现）

- 删除 `config.spendCapUsd` 及其自动关停分支。`/control/state` 仍返回 `spentUsd`，
  但**只作展示**，不再是关闭条件。
- 依据：订阅制下 cache-read 在 5h 窗口内几乎不计配额；按 API 公开价
  （未命中 $3/M、命中 $0.3/M）累计的"总额"会误杀大前缀保温 ——
  531k 前缀单次 ping 估算 **$0.16**，旧 $1 上限 **6 次就关停**（约 2.6 小时）。
- 系统层配套：`~/.config/systemd/user/kimi-cache-sidecar.service` 里
  `Environment=SPEND_CAP_USD=50` 已随本改动移除语义（保留无害，代码不再读取）。

### 2）仅保留单次 hit 墙（✅ 已实现）

自动关闭（`on=false`）现在**只剩两条**：

| 判据 | 参数 | 行为 |
|---|---|---|
| **单次命中率不足** | `HIT_RATIO_MIN`（默认 5%） | 一次 ping 的 `cached/prompt < 门槛` → 立即 off |
| 凭据/配额硬错误 | — | 401/403 立即 off（重试无意义） |

**transport 失败不再自杀**：429/5xx/超时只走 +2min/+4min 快速 retry，retry 耗尽置
`stale`（暂停，`on` 保持 `true`），下一次真实请求到达自动复活。
依据：网络抖动与「缓存没保住」是两件事，混为一谈会误杀保温。

### 3）历史会话重分配独立 key + HB 前交叉校验（✅ 已实现）

**key 改为会话级唯一、确定性派生**（两端算法必须逐字一致）：

```
key = "dshsc-" + sha256("session:" + sessionId).slice(0,16)
```

- 与 system prompt 内容完全解耦 → **KI-3 根治**（system 怎么变，key 不变）；
- 不同会话必然不同 → **KI-1 根治**；
- 插件不再"解析/猜测"key：`resolveSessionKey(sessionId)` 就是纯函数推导。
  **旧 recency 策略与 `dshsc-${sessionId.slice(0,16)}` 伪造兜底已全部删除**。

**sidecar 端识别会话的优先级**（`keySource` 字段写入遥测，便于审计）：

| 优先级 | 来源 | keySource |
|---|---|---|
| 1 | `prompt_cache_key` | `prompt_cache_key` |
| 2 | `metadata.user_id`（`dsh:session-x` 或裸 `session-x`） | `user_id` / `user_id-key` |
| 3 | **user 消息文本**里的 `session-<uuid>` | `messages-scan` |
| 4 | system 前缀哈希（仅兜底） | `system-hash` |

> 第 3 条的两个硬约束（2026-10-21 自查坑）：
> ① **只扫 role=user 的消息** —— assistant 回复里常引用别的会话 id，
> 一并扫描会把本会话绑定到被引用的会话上；
> ② 同一条消息出现多个 id 时，优先取紧跟「会话 ID：」标记的那个。

sidecar 同时把解析出的会话标识**写回请求体** `metadata.user_id`，
使 `/control/verify` 能事后反查「这个 key 属于哪个会话」（事故取证依据）。

**交叉校验 `POST /control/verify`（新增端点）**：开启保温前必须三条全过，否则**拒绝开启**
并如实回报（绝不假装 ACTIVE）：

1. 该 key 有已记录的真实请求体；
2. 请求体里的会话标识与目标 sessionId 一致；
3. 观测到的 prompt 规模落在 `expectedPromptTokens ± 25%`。

第 3 条是识破"key 打错对象"最直接的一刀：90 token 的测试前缀 vs 531k 的真实会话，一眼可分。

**reconciler 兜底**：每轮对账都重算派生 key，发现 `state.json` 里存与推导值不符 →
立即 `off` 旧的错误 key、写入正确 key 并留 `rekeyedFrom` 痕迹（10-21 事故的机制层堵漏）。

### 4）会话 id 动态加载（10min + 事件驱动）（✅ 已实现）

- reconciler 周期：**60s → 10min**（`intervalMs = 10 * 60 * 1000`）。
- **事件驱动优先于轮询**：订阅 `session/created`、`session/disposed`、`workspace/session-stop`，
  任一触发即立即重扫；重扫请求合并（刷新中再来的请求只置 pending，不排队堆积）。
- 分层缓存（KI-4 一并修掉）：
  - **全量会话列表**（贵，可能解压日志）→ reconciler 快照，10min/事件刷新；
  - **归档集合**（内存数组，成本≈0）→ 每次请求实时读 →
    **归档/取消归档立刻生效**，不必等快照。
- **标题缓存**：60s TTL 兜底 + 订阅 `session/event` 的 `session/title` 事件精确失效 →
  轮询不再重复折叠大日志（原 KI-4 的 8-9s/次），同时 **Rename 立刻同步**。

### 5）修正已知 HB 错误与保留注意点（✅ 已实现）

| 项 | 状态 |
|---|---|
| KI-1 亲和键碰撞 | ✅ 根治（会话级 key） |
| KI-3 key 漂移 | ✅ 根治（key 与 system 解耦） |
| KI-4 state 接口 8-9s | ✅ 修复（全量列表快照 + 标题 60s 缓存 + 事件失效） |
| KI-7 花费上限 | ✅ 移除（本次裁定 #1） |
| transport 失败误自杀 | ✅ 修复（只 retry/暂停，不 off） |
| `dshsc-${sessionId.slice(0,16)}` 伪造 key | ✅ 删除（会让 sidecar 永久 waiting） |
| recency 猜 key | ✅ 删除（多会话并发必错） |
| KI-2 重启丢请求体 | ⚠️ **未做持久化（有意）**：请求体含完整 prompt，落盘需另立 retention 策略；现以「真实请求到达自动恢复 waiting」缓解。副作用：重启到下次真实请求之间无法 ping（缓存只活 28–45min，间隔太长就白冷读）。 |

**仍然有效的注意点（勿改）**：

- ping 的 `max_tokens` 固定 16（实测 1 不参与前缀缓存）；
- TTL 注入按协议分派（Chat Completions 用 `prompt_cache_options`，Anthropic 用 `cache_control`）；
- **缓存实际存活 28–45min，不是 1h**（实测，见 TTL-FINDINGS.md）→ 间隔建议 25–30min；
  `/HTO` 在 ≥40min 时给出告警；
- `/control/on` 幂等短路（防 reconciler 白 ping）；
- 401/403 急停（凭据问题重试无意义）。

# 追加：持久化重写 + 启动自检（2026-10-21 晚）

## 一、为什么"请求体这么容易丢"

用户质疑："如果请求体这么容易丢失那保温有何意义？"——成立。旧持久化有**三处结构性缺陷**：

| # | 缺陷 | 后果 |
|---|---|---|
| ① | `persistBodies()` 只写 `pings.get(key).on === true` 的条目 | 刚拿到 body、还没 on 的 key 被静默跳过 |
| ② | 用「当前内存快照」**整体覆写**文件 | 任一次扫描时内存为空 → 磁盘被写成 `{}`（19:53/19:54 两次重启就是这么丢的） |
| ③ | `/control/on` 的 409 早退路径**没有落盘** | "开启保温意图"重启后消失，UI 以为开着，实际什么都没 |

**修法：把"快照覆盖"改成"读旧文件 → 合并 → 写回"。** 删除只允许两条合法途径：
显式 `/control/off`、超过 12h TTL。**"扫描为空"永远不再触发删除。**

另补：`pings.json`（保温开关状态）也持久化 —— 只恢复 body 而不恢复 ping 循环，
重启后仍要等插件 10min 对账，而缓存只活 28–45min，这段空窗足够让它过期。

## 二、启动自检（`GET /selfcheck` + 面板报警区）

理念：**"看起来正常"是最危险的失败态**。10-21 事故里 UI 显示 34 次 `hit`，
实际保温打在 90 token 的测试前缀上。故把所有"状态自相矛盾"显式成 alarms：

| code | 含义 | 级别 |
|---|---|---|
| `missing-body` | on=true 但无请求体 → 无法 ping | error |
| `ping-loop-missing` | on=true 且有 body，但定时器不存在 → 循环已死 | error |
| `body-not-persisted` | 内存有 body、磁盘没有 → 下次重启会丢 | warn |
| `stale-no-traffic` | >45min 无真实请求（缓存实测寿命上限）→ 保温大概率已失效 | warn |
| `tiny-prefix` | 前缀 <2k token → 极可能是测试/错误 key | warn |
| `state-diverged` | 插件与 sidecar 的开/关状态不一致（被绕过操作过） | warn/error |

`state-diverged` 是专门为"我自己犯的错"加的：手工调 `/control/on` 绕开插件后，
插件记录 off、sidecar 却在保温 —— 这种分叉以前完全看不出来。

启动时自检结果打印到 journald，同时挂在 `/control/state.selfCheck`，
插件按 sessionId 归位到每个会话行的 `alarms`，HB 面板顶部渲染红色报警区。

## 四、仍然存在、无法根治的

1. 缓存实测只活 **28–45min**（非 1h）→ 间隔应 ≤25min，`/HTO` 在 ≥40min 告警；
2. 缓存过期后第一次 ping 必然全价冷读 —— 物理限制；
3. `sessions`（前缀观测）不持久化，重启后 `promptTokens` 显示"未观测"，仅为遥测；
4. KI-1 兜底路径（无任何 session 标识时退回 system 哈希）仍可能碰撞，
   需 DSH core 在请求中注入 session id 才能根治。
